## 二、逐条详析

### 1. 四层指标体系 —— 已覆盖

调研文档 §3.3 定义四层：检索层（nDCG@k/Recall@k/MRR/Hit@k/Completeness@k）、选择层（Tool Selection Accuracy/Argument Correctness/Format Correctness/Executable Rate）、端到端层（Task Success Rate/Step Accuracy）、Judge 层（G-Eval/DAG/Faithfulness）。

设计稿 §6 指标表的映射：

| 调研四层 | 设计稿对应 | 位置 |
|---|---|---|
| 端到端层 | `safe_success` 主指标（= Task Success Rate 的安全化：终态+终止行为+零禁止副作用+预算内） | §1、§6 |
| 检索层 | coverage@W / coverage@k / 充分资源覆盖（诊断位） | §6 |
| 选择层 | 错工具、错参数、越权尝试/副作用、错误拒绝率（比调研多出越权与拒答两个 e2e 特有维度） | §6 |
| Judge 层 | 确定性证据检查优先，机器无法判定才用盲化 LLM 裁判 + 人工标注集校准 | §5 |

定位差异是**有意的语境转化**而非缺失：端到端评测里排序质量指标（nDCG/MRR）只配做诊断，主指标必须落在任务结果上。这与调研文档 §1.1"ToolBench/Gorilla 主要测端到端、检索只是子组件"的分层逻辑一致。
可选补丁：设计稿可加一句"排序质量细粒度指标（nDCG/MRR）由离线检索基准线（ToolRet/SkillRet 适配器）负责，e2e 只报 coverage 类诊断"，把分工写死。

### 2. A/B candidate 管线 —— 已覆盖

调研文档 §3.4① 要求 baseline 与 candidate 各产结果文件、逐格对照、分组计算（all/zh/en/mixed）。设计稿 §4 的实现更强：A0/A1/A2/A3 四组、"组间除检索决策外配置一致"、逐例配对 `mean_r(success_A1) − mean_r(success_A0)`、配对改善/退化/持平计数、预注册增益门槛（§6）。差异仅在分组维度：调研按语言分组服务"中英分别卡（防隐蔽退化）"（决策表 #8），设计稿按 suite×slice 分组、多语言只是 slice 之一（§3.1 "若真实流量存在"）。若留出集纳入多语言用例，应把语言升为必报分组并在退化容忍度里分别卡。

### 3. bootstrap 95% 置信区间 —— 已覆盖

设计稿 §6 的成簇 bootstrap（以用例为抽样单位、改写族作更外层抽样单位、三次重复不拆开计独立样本）在方法上严于调研文档 §3.4② 的"固定种子重采样"；"置信区间跨越零→证据不足→追加独立样本"的解读规则也与调研"A/B 差异必须在置信区间外才算显著"同义。缺口仅是字面：未写明 95% 置信水平与随机种子固定。建议补一句，防止事后选择置信水平。

### 4. 确定性保证 —— 已覆盖（语境转化）

"候选向量预计算缓存固定版本"在设计稿中的等价物是 §2.2 "允许复用**只读且版本固定**的语料嵌入快照"与 §4 冻结清单中的"嵌入模型和向量快照"，§7 还要求记录嵌入版本。ONNX+CPU+fp32 属于 agent-retrieval 库的推理内核实现手段（本仓确定性 BM25 内核 + write-once 向量快照已承担），e2e 稿职责是冻结版本号与快照哈希，不必规定内核。
需要指出的真正差异：e2e 的非确定性主源不是嵌入而是 Agent LLM 与 Jev 的采样，设计稿用"冻结模型标识与采样设置 + 每例 3 次重复 + pass^3 + 成簇 bootstrap"统计包裹残余随机性——这是端到端语境下唯一可行的路线，成立。可选补丁：§4 或 §7 加半句"一阶段检索输出可由目录版本 + 嵌入快照哈希完全复现"，把 e2e A/B 的可复现前提显式闭环。

### 5. CI 零退化门控 —— 不适用（精神已吸收）

调研文档 §3.4④ 的门控面向**检索内核回归防护**：改内核/评测代码时自动运行、逐格比较、对抗集测负例、fixtures 入库离线跑，且自承"真实零退化待首次金版本保存后才正式启用"。设计稿是**一次性预注册决策实验**：留出集冻结后跑配对组，回答"是否采用 Jev"。两者的运行频率、触发条件、成本模型都不同，把 CI 门控塞进 e2e 稿属于范围错误。
三个子项的精神在设计稿中的转化：

| 门控子项 | 设计稿对应 |
|---|---|
| 对抗集负例检测 | 无匹配/无权限 slice 作为必报分组 + §6 预注册"负例/权限退化容忍度"（plan 另有 "Retain negative-case and permission-case rates as separate guardrails"） |
| 金版本 baseline | A0 明确指定的参考基线 + 全配置冻结 + §7 全轨迹存档（具备事后成为金版本的形态） |
| 逐格比较 | 逐例配对 + 改善/退化/持平用例计数 |

前瞻性口子（首轮不做）：若 e2e 评测将来常态化（目录/内核每次更新重跑），可把首份 A0 冻结结果存档为金版本、后续候选与其逐格比较——这与调研文档"先产金版本再启用门控"的顺序一致。

### 6. LLM-as-judge 偏见控制 —— 可增强（最高优先级缺口）

设计稿 §5 已有四项控制：使用范围最小化（确定性终态检查优先）、盲化（裁判不知变体名，plan 明文）、人工标注集校准、评分器与 Agent/Jev 隔离。对照调研文档 §3.4⑤ 与决策表 #6 的三件套（DAG / 多模型交叉 / 固定 prompt 与温度），缺口：

1. **裁判模型标识、judge prompt、采样温度未列入 §4 冻结清单**。§4 冻结了 Agent 模型与采样设置、Jev 问题/版本，唯独裁判环节没有对应条目——设计稿中唯一未做版本冻结的 LLM 环节。这是必补项。
2. **多模型交叉/分歧处理规则缺失**。首轮 80 例规模下单裁判 + 人工校准未必不够，但应写明：裁判判断与校准集人工标签的分歧率超阈值时如何处理（降级人工复核 / 换裁判重跑），避免临场裁量。
3. **DAG 是工具级选项而非必选**。已核实（见"四、事实核实"）：deepeval 自 v3.48 起提供 DAG 类确定性 judge（决策树结构、节点为 LLM 判定）。设计稿不必绑定 deepeval，但若引入结构化 judge，判定路径应随轨迹存档（§7 的 Jev 原始判断字段旁加裁判判定路径即可）。

### 7. Completeness@k —— 已覆盖

调研文档 §3.3 定义 Completeness@k = 多 skill 查询中 Recall@k=1 的 query 占比，用于防"部分召回"被 Recall@k 均值掩盖。设计稿的三处合力构成其任务化等价物：§3 用例 `gold_resource_ids` 为数组（示例 tool-017 需 review.find_slot + review.schedule 两资源）；§6 检索诊断"充分资源覆盖"；§5 失败归因明确"充分资源集合需人工定义，不能从一个 gold ID 推断"。且设计稿口径比基准口径更贴合现实（gold 未必是唯一可行路径）。可选：报告措辞上把"充分资源覆盖"与 Completeness@k 互认标注，便于与调研文档/基准读者对齐。

### 8. 两档设置（w/ inst. vs w/o inst.）—— 不适用

调研文档 §3.2/§3.5 要求接入 ToolRet 时必须保留两档对照，因为它度量"query 信息量这一检索难度维度"。该维度属**离线检索层评测**，本仓 ToolRet 适配器按基准口径承担。e2e 语境下：用户任务天然含完整意图（w/ inst. 的端到端形态），而 Agent 自行构造/改写搜索 query 恰是 w/o inst. 场景的 agent 侧体现——但 query 构造 × 检索质量的复合正是被测的端到端行为，设计稿 §4 明文"Agent 自主改写 query 时两组的后续轨迹可能不同，这是端到端效果"，另有"固定 query 的离线回放"定位差异，已覆盖两档设置想分离的两种影响。拆档冻结反而破坏端到端语义。
建议加一句分工说明（§3.1 或 §6）："ToolRet 的 w/inst 与 w/o inst 两档结论由离线基准线负责；e2e 中 Agent 自写 query 造成的检索难度差异归入端到端效果，不单独设档"——防止后续评审者误判为遗漏。

### 9. Cohen's κ 标注一致性 —— 可增强

调研文档 §3.2 后续路径与 §3.6 构件表要求 ground truth 重建"用 Cohen's κ 控一致性、双人标注配对、回填校验"。设计稿 §3.1 要求"逐例补齐工具语义、初始状态、权限、预期终态和独立人工审查"，§8 阶段 3 通过条件是"充分资源和终态经过第二人审查"——双人环节存在，但停留在"有人复核"，没有量化一致性门槛与分歧仲裁。
具体建议（落在 §8 阶段 3 与 §3.1）：`required_state`/`forbidden_effects`/充分资源集合由两人独立标注，报告条目级一致率与 Cohen's κ（判定为多元/有序时可换加权 κ 或 Krippendorff's α），κ 低于预设阈值的用例进入仲裁，仲裁后冻结。80 例规模下成本可控，且这正是设计稿 §8 阶段 3"数据冻结"通过条件的自然强化。

### 10. 成本/延迟指标 —— 已覆盖

设计稿 §6 效率行（p50/p95 时延、模型/嵌入/Jev tokens、费用、搜索与执行调用次数、冷/热缓存分报、Jev 降级率）覆盖调研决策表 #10 的"token 成本与 p50/p99 延迟"，且粒度更细。p95 与 p99 的差异是分位数选择：首轮约 480 episodes，p99 落在约第 5 个最差样本，估计方差过大，p95 是合理工程选择；可在文中注一句理由（可选，不改也成立）。

## 五、最重要的 3 条修改建议（回填设计稿时采纳，本次不改设计稿）

1. **裁判环节入冻结清单**（条目 6）：§4 冻结清单补"裁判模型标识、judge prompt、采样温度"；§5 补裁判与人工校准集分歧率超阈值的处理规则（降级人工复核或换裁判重跑），必要时 §7 轨迹字段加裁判判定路径。
2. **标注一致性量化**（条目 9）：§3.1 与 §8 阶段 3 把"独立人工审查/第二人审查"升级为双人独立标注 + 一致率/Cohen's κ 报告 + 分歧仲裁后冻结，作为数据冻结阶段的量化通过条件。
3. **统计与复现前提显式化**（条目 3/4）：§6 写明"bootstrap 置信区间取 95% 水平、固定随机种子"；§4 或 §7 补半句"一阶段检索输出可由目录版本 + 嵌入快照哈希完全复现"。

次要建议（不入 top 3）：留出集含多语言用例时把语言升为必报分组并分别卡退化容忍度（条目 2/决策表 #8）；§3.1 或 §6 加两档设置的分工说明（条目 8）；§7 留纵向评估口子一句（决策表 #9）；"充分资源覆盖"标注 Completeness@k 互认（条目 7）。
